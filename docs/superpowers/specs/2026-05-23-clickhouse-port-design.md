# ClickHouse Port — Design Spec

Date: 2026-05-23
Status: Approved

## Goal

Replace the Google Sheets CSV ingestion with direct ClickHouse queries against the existing `hbshengma.deliverydetail` table. Eliminate the 2 MB Next.js fetch-cache warning, remove the dependency on a public spreadsheet, and make the data source the database that already holds the canonical transaction stream.

## Background

`lib/sheets.ts` currently fetches two CSV exports from a public Google Sheets document on every revalidation. The "database" tab has grown beyond 2 MB, so Next.js refuses to cache it (`Failed to set Next.js data cache ... items over 2MB can not be cached`); every request re-fetches the spreadsheet over the network. The same transactional data lives in a ClickHouse instance the user owns. This spec moves the dashboard to query ClickHouse directly.

The four dashboard routes that depend on transaction data — `/dashboard`, `/executive-summary`, `/database`, `/sales-report` — share the existing `Transaction[]` → `aggregateTransactions` / `filterTransactions` / `filterByDateRange` pipeline. The port keeps that pipeline intact and only swaps the source of `Transaction[]`.

## Decisions (from brainstorming)

- **Database:** ClickHouse, table `hbshengma.deliverydetail`, queried over HTTP (port 8123) with credentials in `.env.local`.
- **Fetch strategy:** A — drop-in replacement. Server components fetch the full `Transaction[]` from ClickHouse and pass it to the existing client components. `aggregateTransactions` and `filterTransactions` run unchanged in TypeScript. No server-side aggregation in this iteration.
- **Currency UX:** USD ⇄ KHR toggle in the page header (mirror of `ThemeToggle`). State is client-side and persisted in `localStorage`. Default KHR (the active currency at 2026-05-23). One currency at a time — all KPI cards, charts, and tables continue to render a single number per slot, just sourced from the selected currency.
- **Location:** static `device_id → location` map in code (`lib/locations.ts`). Starter values generated by querying CH for distinct device_ids and their latest `device_name`; the user reviews and edits.
- **Category:** static `product_name → category` map in code (`lib/categories.ts`). Starter values generated by querying CH for distinct product names; the user reviews and edits.
- **Device-name volatility:** the same `device_id` appears with several `device_name` values over time. `device_name` displayed in the UI comes from `anyLast(device_name)` per `device_id` so each machine has one consistent name.
- **Currency tagging:** per-row currency is derived from `sales_time`. `sales_time < '2026-05-19'` → `USD`. Else → `KHR`. The cutoff is hard-coded as a single named constant.

## Architecture

### Data flow

```
ClickHouse hbshengma.deliverydetail
        │  fetchTransactions()  (lib/clickhouse.ts)
        ▼
Transaction[] (per-row currency tagged)
        │  passed by server component to client wrapper
        ▼
Client wrapper (ExecSummaryClient / DatabaseClient / SalesReportClient)
        │  currency state (localStorage) + date filter state
        ▼
filterByDateRange / filterTransactions → aggregateTransactions(..., currency)
        ▼
ExecSummaryData → existing UI components (unchanged)
```

### `lib/clickhouse.ts`

Single ingestion module. Uses the official `@clickhouse/client` package (HTTP, not native protocol). Reads connection from env:

```
CLICKHOUSE_URL=http://103.230.81.70:8123
CLICKHOUSE_DB=hbshengma
CLICKHOUSE_USER=hbshengma
CLICKHOUSE_PASSWORD=l1nkit240
```

Exports `fetchTransactions(): Promise<Transaction[]>`. SQL:

```sql
SELECT
  device_id,
  device_name,
  product_name,
  product_brand,
  sales_amount,
  sales_time
FROM hbshengma.deliverydetail
WHERE sales_time IS NOT NULL AND sales_amount IS NOT NULL
ORDER BY sales_time
```

Returns rows as JSON via the client. Wrap the fetch in `next: { revalidate: 1800 }` semantics — `@clickhouse/client` does not integrate with Next.js cache, so a manual in-process cache wrapping `fetchTransactions` with a 30-minute TTL is added to `clickhouse.ts`. (This also avoids the >2MB Next cache limit entirely — the response stays in process memory.)

### `lib/transactions.ts`

Two pure helpers:

```ts
const CURRENCY_CUTOFF = '2026-05-19' // KHR effective from this date onward

export function rowCurrency(salesTime: string): 'USD' | 'KHR' {
  return salesTime < CURRENCY_CUTOFF ? 'USD' : 'KHR'
}

export function rowToTransaction(row: CHRow): Transaction
```

`rowToTransaction` maps a ClickHouse row to the existing `Transaction` shape:

- `machine`        ← `device_name`
- `location`       ← `DEVICE_LOCATIONS[device_id] ?? 'Unknown'`
- `product`        ← `product_name`
- `unitPrice`      ← `parseFloat(sales_amount)` (NaN → 0)
- `qty`            ← `1`  (one row = one sale)
- `time`           ← `sales_time.slice(11, 19)` ("HH:MM:SS")
- `date`           ← `sales_time.slice(0, 10)` reformatted to `M/D/YYYY` so `parseTransactionDate` accepts it
- `currency`       ← `rowCurrency(sales_time)`

### `lib/locations.ts`

```ts
export const DEVICE_LOCATIONS: Record<string, string> = {
  // generated starter, e.g.:
  '9fl9g4hgn0f243c': 'KHMER House',
  'h5k8l6ou81i5wsq': 'RUPP Uni',
  // ... user edits to match the desired location names
}
```

A bin/script (or simply a one-off SQL the implementer runs) seeds this from CH:

```sql
SELECT device_id, anyLast(device_name) AS name, count() AS n
FROM hbshengma.deliverydetail
GROUP BY device_id
ORDER BY n DESC
```

Implementer guesses the location from the name (regex pulls the second `-`-separated token, e.g. "V4 - NPH - ..." → "NPH"), writes the starter map, and asks the user to review before commit.

### `lib/categories.ts`

```ts
export const PRODUCT_CATEGORIES: Record<string, string> = {
  // generated starter, e.g.:
  'BACCHUS': 'Energy Drink',
  'OLATTE': 'Dairy',
  // ...
}
```

Seeded the same way (CH `SELECT DISTINCT product_name`). Implementer makes reasonable category guesses and asks the user to review before commit. Categories not in the map fall through to `'Other'` at consumption time (existing fallback in `aggregateTransactions`).

### `lib/types.ts`

```ts
export type Currency = 'USD' | 'KHR'

export type Transaction = {
  machine: string
  location: string
  product: string
  unitPrice: number
  qty: number
  time: string
  date: string
  currency: Currency
}
```

`KPIs`, `MonthlyRow`, `ProductRow`, `MachineRow`, `WeekdayRevenue`, `DailySales*` shapes are unchanged — each represents a single-currency view.

### `lib/aggregate.ts`

`aggregateTransactions(transactions, categoryMap, currency)` — new third parameter. The function filters `transactions` to `t.currency === currency` first, then runs the existing math unchanged. The signature change is the only behavioural difference.

`filterByDateRange` is unchanged (currency-agnostic).

### `lib/filter-utils.ts`

`filterTransactions(transactions, filters)` — `FilterState` gains `currency: Currency`; the function filters out rows whose `t.currency !== filters.currency` first. The database page filters by the selected currency so the table never mixes units.

### `components/CurrencyToggle.tsx`

Mirror of `ThemeToggle`:

- `'use client'`, useState initialised to `'KHR'`, useEffect reads `localStorage['currency']` on mount and syncs.
- Click toggles between `'USD'` and `'KHR'`, writes to `localStorage`, and dispatches a `CustomEvent('currencychange', { detail: { currency } })` on `window` so already-mounted components re-read.
- Renders a small button styled like `ThemeToggle` and `RefreshButton`: shows `$ USD` or `៛ KHR` plus the alternate as the action label.

The client wrapper components (`ExecSummaryClient`, `DatabaseClient`, `SalesReportClient`) hold a `currency` state initialised from `localStorage` (with a `useEffect` mount sync to avoid hydration mismatch) and subscribe to the `currencychange` event to update. The header just renders `<CurrencyToggle />`.

### Pages

Each of the four pages becomes:

```tsx
import { fetchTransactions } from '@/lib/clickhouse'
// ... existing imports ...

export const dynamic = 'force-dynamic'

export default async function Page() {
  const transactions = await fetchTransactions()
  return (
    <div className="p-4 md:p-6">
      <div className="flex items-center justify-between mb-6 pl-10 md:pl-0">
        <div>{/* h1 + subtitle */}</div>
        <div className="flex items-center gap-2">
          <CurrencyToggle />
          <ThemeToggle />
          <RefreshButton />
        </div>
      </div>
      <SomeClient transactions={transactions} />
    </div>
  )
}
```

Pages no longer compute `categoryMap` — the static `PRODUCT_CATEGORIES` is imported wherever needed. The client wrapper passes `PRODUCT_CATEGORIES` to `aggregateTransactions` (or `aggregateTransactions` reads it directly — implementer's choice, kept consistent across wrappers).

## Currency rendering note

KPI cards, charts, and tables continue to render a single currency at a time. The unit symbol switches with the toggle:

- USD: `$X.XX`, two-decimal.
- KHR: `៛X` (integer riel, no decimals — fractional riel is meaningless).

A small `formatMoney(amount, currency)` helper in `lib/transactions.ts` centralises this so every render site uses the same rule.

## Error handling

- **CH unreachable / 5xx:** `fetchTransactions` throws; the existing page-level `error.tsx` files render the error state. (`/dashboard`, `/executive-summary`, `/database`, `/sales-report` already have `error.tsx` boundaries from earlier work.)
- **Auth failure:** treated as any other fetch error; the error message includes the CH HTTP body for debugging.
- **Empty result:** `transactions` becomes `[]`; existing `aggregateTransactions` handles the empty case and renders a "No transactions found" state.
- **Malformed `sales_amount`:** `parseFloat` returns `NaN`, mapped to `0`. The mapping is per-row — one bad row does not poison the whole load.

## Testing

`tests/` runs in the `node` env on pure logic.

- `tests/transactions.test.ts` (NEW) — verifies `rowCurrency` (cutoff boundary), `rowToTransaction` (field mapping, date reformat, NaN handling), and `formatMoney`.
- `tests/aggregate.test.ts` (EXTENDED) — adds cases that mix USD + KHR rows and verifies `aggregateTransactions(..., 'USD')` returns only USD totals.
- `tests/filter-utils.test.ts` (EXTENDED) — verifies `filterTransactions` filters out rows of the non-selected currency.

The ClickHouse client itself is not unit-tested (network); a successful end-to-end render of `/dashboard` against the live CH instance is the acceptance test.

## Migration / cleanup

- Delete `lib/sheets.ts`. No other module imports it after the port.
- Remove the Google Sheets URL constants and all related code.
- Remove `next: { revalidate: 1800 }` reliance for transactions (replaced by the in-process cache in `clickhouse.ts`).
- `app/actions.ts`'s `revalidateSheets` is renamed to `revalidateData` (or similar) and clears the in-process cache so the existing "Refresh Data" button still works.

## Out of scope

- Server-side aggregation in ClickHouse (Approach B). Revisit if the row count grows past ~200k.
- Side-by-side dual-currency rendering. Toggle covers the requirement with much less rework.
- Writes to ClickHouse — the dashboard stays read-only.
- A `product_categories` table in ClickHouse — static map in code is enough at current product count.
- Auto-dedup of identical sales rows that may be scraped multiple times — handled upstream by the dumper; out of scope here.

## Concern protocol

During implementation, the implementer surfaces a **concern** explicitly (not silently) when about to do any of:
- A schema change that breaks downstream code.
- Anything irreversible (data deletion, force-push, history rewrite).
- A change that widens security surface (logging credentials, exposing CH URL to client bundle, etc.).
- A workaround that materially deviates from this spec.

The user reviews the concern before the change is committed.
